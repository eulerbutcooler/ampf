## Why does a reverse tunnel exist?

Imagine you're developing a webapp for a client and want to show it to them, you have 2 options - **A. Deploy the site** \
or \
**B. Give them the code and ask them to run it on their machine**. \
But why can't we just give them our public IP and the port the webapp is locally running on? \
That doesn't work because the machine usually has a private IP address and unsolicited inbound connections may not have a forwarding rule. \
So what do you do?
You flip the direction of the connection. \
Instead of asking the internet to initiate a connection to your laptop, you initiate a connection to a server that is publicly reachable. \
You make an *outbound connection*, which in this case, is the deployed instance of **Surang**.

## What Surang actually consists of

Surang consists of two major components: **Server** and **Client**

<Figure
  src="/figures/surang-client-server.svg"
  alt="Architecture diagram: the Surang Client on the developer machine keeps a persistent outbound connection to the Surang Server on a VPS, where a public listener routes visitor traffic through the tunnel; a separate API stores users and tokens in SQLite."
  caption="Client and server - one persistent outbound connection, and visitor traffic routed back down it"
/>

**surang-server** runs on the VPS. It assigns hostnames to tunnels, receives public traffic and routes it. \
**surang-client** runs on the developer's machine. It registers tunnels, maintains the connection and forwards traffic to local services. 

User accounts and credential data are stored in SQLite so Surang doesn't need a separate database server. The server can be distributed as a single executable while the SQLite database remains a separate file. \
Active tunnel sessions and hostname-to-tunnel mappings are stored in an *in-memory registry* and are ephemeral in nature.

## Why TCP multiplexing
I wanted multiple tunnels to share a persistent TCP connection instead of opening a separate connection for each one.\
Why, you may ask? \
Well let's just say TCP connections are *thicc*. Each connection comes with its own state, buffers and resource overhead. Multiply that across hundreds or thousands of connections and they can quickly eat up the memory on the VPS. Managing them would be a task in itself. \
Another problem is TCP itself is a byte stream and not a message-based protocol. It doesn't preserve message boundaries, so we need a way to determine where one message ends and the next begins. To carry multiple independent streams of traffic over a single connection we also need a way to frame and distinguish those streams. \
So I used [Yamux](https://github.com/hashicorp/yamux). It enabled one TCP connection per client and multiple logical streams per connection. 
<Figure
    src="/figures/tcp-multiplexing.svg"
    alt="Architecture diagram showing TCP multiplexing using Yamux"
    caption="One persistent TCP connection carries multiple independent Yamux streams, including concurrent visitor requests."/>
The server listens on port 5555 and accepts incoming TCP connections from Surang clients. Each client establishes one persistent TCP connection over which Yamux session is created. \
Because the client initiated the connection, the server can send visitor traffic back through that existing connection without requiring a new inbound connection to the developer's machine.
This way, Surang reuses the existing connection allowing control messages and concurrent tunnel traffic to share the same transport. \
Each Yamux stream has its own stream ID. Yamux also uses protocol flags to manage stream states and lifecycle events. 

## How surang's client and server communicate

Yamux transports streams but it doesn't tell Surang which local application to dial. Surang needs its own application-level protocol on top. This is where registration and dial messages come in.
**Registration** - Tells the server what exists locally
Consider the command -
```bash
surang-client -tunnel web=localhost:3000
```
The client needs to tell the server that it wants to expose a tunnel labelled web. The local destination **localhost:3000** is meaningful to the client but not to the server.\
The client sends this JSON registration frame:
```json
{
  "secret":"TOKEN",
  "tunnels":[
    {
      "id": "web",
      "scheme": "http"
    }
  ]
}
```
We didn't send the localhost address because the server doesn't need to dial to it on the client's behalf. The client does it. \
The server responds with an **ACK** 
```json
{
  "results":[
    {
      "id": "web",
      "host": "meow-pilot-live.surang.xyz"
    }
  ]
}
```
When a visitor's request arrives, the server opens a new Yamux stream and sends a **Dial** frame identifying which registered tunnel should handle the request:
```json
{
  "tunnel_id":"web"
}
```
The client uses this label to look up the corresponding local destination in its configuration. The server doesn't need to know the local address; it only needs to know which client session and tunnel label to route the request to.

## What the request lifecycle looks like
**PHASE A - The Client registers and establishes a session.**
<Figure
    src="/figures/surang-client-initiate.svg"
    alt="Client mints a token and dials out to the server, registers its tunnels and receives the hostnames."
    caption="The client authenticates with the server, receives a token, establishes a connection, registers its tunnels and receives public hostnames"
/>
The user creates an account by running this,
```bash
surang-client login
```
which opens this menu:
<Figure
    src="/figures/surang-tui.png"
    alt="Surang's terminal interface for configuring account and server details."
    caption="The CLI guides the user through connecting to a Surang server"
/>
The user enters their details and in the server section they put the API URL of the hosted surang server, which, in our case is ***https://api.surang.eulerbutcooler.xyz***. \
This sends a POST request to the API of surang. The server mints a token and the user gets it back. It is then stored on their PC. The token's expiry can be set to an hour, a day, a week or forever. \
The server stores the user's email and hashed password in SQLite, along with a hash of the issued token for auth. \

The user can then register their tunnels using
```bash
surang-client -tunnel web=localhost:3000 srv=localhost:4000
```
This command hits the port 5555 on the server. The client establishes a persistent outbound TCP connection to the server. \
1. This client sends a Register Frame which has the token and services they want to register - "web" and "srv". 
2. The server then authenticates the token against the database.
3. It then generates a three-word subdomain (like [what3word](https://what3words.com/)) and checks Registry for collision.
4. If the three-word string is available it is stored in the mapping.
5. The server sends an ACK back to the client with the URLs for their tunnels.

**PHASE B - A visitor makes an HTTP request**
<Figure
    src="/figures/surang-visitor.svg"
    alt="Lifecycle of an HTTPS request on a subdomain"
    caption="A visitor’s HTTP request travels through the tunnel to the local web app, and the response returns over the same Yamux stream."
/>
1. DNS resolves the public hostname to the Surang server's address.
2. The server terminates HTTPS on port 443, extracts the subdomain from the request's Host header.
3. The server looks up the subdomain in the active registry to find the client's Yamux session and tunnel label
4. The server opens a Yamux stream and sends a *Dial* frame identifying the target tunnel.
5. The client maps the tunnel label web to its configured local address and forwards the HTTP request to that service.
6. The local service's response travels back through that same stream and is returned to the visitor.

## Design Decisions

### In-memory registry
The hostnames/URLs are stored in the *in-memory* registry. I used two maps for mapping them.
**Map 1**: *sessions - subdomain to binding*
```go
sessions map[string]Binding
type Binding struct {
	Session *yamux.Session
	Label string
}
```
This map is for forward lookup and is used to route public traffic. \
If two tunnels are registered by the same client, it maps the subdomains to the session and the label. \
Example:
```go
sessions["meow-pilot-wow"] = Binding{
    Session: sessionA,
    Label:   "web",
}

sessions["new-vigil-blunt"] = Binding{
    Session: sessionA,
    Label:   "srv",
}
```
**Map 2**: *tunnels - session to its subdomain*
```go
tunnels map[*yamux.Session][]string
```
This map is for the reverse lookup and is used primarily for cleanup. \
The `Key` is the client's `*yamux.Session` (a pointer to the yamux session) and `Value` is a list of every subdomain registered by that session. \
Example:
```go
tunnels[sessionA]=[]string{
	"meow-pilot-wow",
	"new-vigil-blunt",
}
```
When sessionA disconnects, Surang can retrieve all of its subdomains instead of searching through every entry in `sessions` (map 1) \
`Unregister()` function then deletes each subdomain from *map 1* and removes the session from *map 2* \
Both maps are protected by a shared `RWMutex` (read-write mutex) and are updated together during registration and cleanup. \

### HTTP proxying
I used Go's `httputil.ReverseProxy` with a custom `RoundTripper` called `tunnelTransport`
The standard reverse proxy handles the HTTP request and response mechanics, while my custom transport changes how requests reach the backend. Instead of making a regular network request to the destination, tunnelTransport opens a Yamux stream to the appropriate client and sends a Dial frame identifying the target tunnel. \
The selected tunnel binding is attached to the request context, allowing the transport to find the right Yamux session and tunnel label for each request. Once the stream is established, the HTTP request is forwarded through it, and the response is read back from the same stream. \
This approach let me reuse Go's existing HTTP proxy implementation rather than building the entire proxy from scratch.
**Why not implement the proxy myself?**
I could've gone with it but I already built it in another project of mine - [HTTP server from scratch in Go](https://github.com/eulerbutcooler/http-server) so I skipped it in this one.

### Three-word Subdomains
Initially I was fine with subdomains containing numbers and letters but they didn't feel very human-readable. So I went with three-word subdomains. \
The generator uses **rejection sampling** to implement **sampling without replacement**. Whenever it picks an index that has already been selected, it rejects it and draws another one.\
So you'll never get a subdomain like *meow-meow-meow* (sorry) \
The hostnames can be re-minted once they are unregistered.
The wordlist contains 1000 unique words and is embedded into the executable binary, so there's no separate wordlist file to ship or load at runtime.

### Wildcard DNS
Since Surang generates subdomains dynamically, creating a separate DNS record for every tunnel wouldn't be practical. Instead, Surang uses a wildcard DNS record(*.surang.eulerbutcooler.xyz) that points generated subdomains to the server. \
This means a hostname like *meow-pilot-live.surang.eulerbutcooler.xyz* can resolve to the Surang server without needing its own DNS record. \
In TLS mode, Surang also uses a wildcard TLS certificate that covers the root domain and its single-level subdomains. So all the subdomains are HTTPS secured.
